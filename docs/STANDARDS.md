# 项目规范

版本：1.1 · 更新日期：2026-11-01。

适用于本轮及后续的内容、设计、代码与素材维护。现有文件按实际修改范围逐步对齐，不为满足格式一次性重排整个仓库。

## 1. 文档各自负责什么

| 文件 | 维护内容 |
| --- | --- |
| [README](../README.md) | 人的入口：项目介绍、预览方法、文件分工与常见操作 |
| [AGENTS](../AGENTS.md) | AI 的入口：阅读顺序、执行流程和边界 |
| 本文件 | 内容、来源、素材、编码及验证标准 |
| [COLLABORATION](COLLABORATION.md) | Git 同步、冲突整合与 PR 交付步骤 |
| [OWNER-AGENT-START](OWNER-AGENT-START.md) | owner 可转交的接手提示词及交付状态解释 |
| [PR 模板](../.github/PULL_REQUEST_TEMPLATE.md) | 双方 agent 交接具体任务的共同字段 |
| [DECISIONS](DECISIONS.md) | 影响后续工作的决定、依据与替代关系 |
| [PROJECT](PROJECT.md) | 当前阶段、已完成项、剩余事项与下一步 |
| [OPTIMIZATION-PLAN](OPTIMIZATION-PLAN.md) | 分阶段目标与计划，不充当已实现状态 |

规则只在负责它的文档完整维护，其他文档用链接引用。Git 历史记录代码变化，无需额外复制一份流水账。

## 2. 来源与状态

区分“业务事实”“设计决定”“当前实现”“建议／待确认”。状态不能因为写进代码或合入分支就自动升级。

| 信息 | 核对依据 |
| --- | --- |
| 当前任务范围与新要求 | 当前用户明确指令；影响长期协作时同步文档 |
| 个人职责、指标及统计范围 | 对应项目最新明确确认的文稿、README、开发交接或新增确认记录 |
| 历史作品内容 | 原图、PDF、视频及其来源说明；历史传播表达不等于本次独立验证的科学或效果结论 |
| 当前页面与交互 | 当前分支代码、内容数据及实际验证结果 |
| 改版方向和长期取舍 | 决定记录与优化计划中的显式状态 |

不以文件修改时间或提交先后单独裁定事实冲突。先比较具体确认内容、来源与适用范围；无法确定的部分明确保留未知。

项目内容先读各自目录的 `project.md`、`README.md` 与 `developer-handoff.md`；缺少某文件时使用已有入口。精华油优先使用 `portfolio-content/essence-oil/`，旧入口保留兼容。

旧文档中描述单次交付范围的句子不作为永久限制。历史实现与最新决定不同，可在当前授权范围内调整，并记录有长期影响的变化。

## 3. 网页发布内容

当前发布入口保持清楚：

| 内容 | 当前维护位置 |
| --- | --- |
| 五个案例的主体、职责、成果和作品链接 | `portfolio-2026-content.js` 的 `PROJECTS` |
| 案例开篇标题、侧重点与摘要 | `portfolio-2026.js` 的 `PROJECT_INTROS` |
| 海报线稿、成品及对应说明 | `portfolio-2026-wireframes.js` |
| 原始资料、事实依据与详细分析 | 各项目的 `portfolio-content/` 目录 |

修改同一项事实时，检查上述发布位置与相关项目稿的一致性。`content.json` 是各项目既有结构化资料，目前不是自动生成网页的唯一数据源；不要只修改它就宣称页面已更新。

本轮不先创建另一套平行文案或数据目录。以后采用生成流程或迁移内容格式时，在同一任务中说明新入口、旧入口去向、生成命令及验证方法。

## 4. 内容与文案

- 清楚表达目标读者、项目问题、本人判断、交付物与作品证据；渠道和素材服务于叙事。
- 五个项目保留可访问入口。各案例可以采用不同结构，不强行复制同一套段落。
- 区分本人撰写／策划、统筹审核与团队制作，不增添未经确认的设计、拍摄、剪辑、商务或投放职责。
- 指标保留对象、时间、渠道、统计范围及归因边界。未知时间不补填，不同口径不相加，团队成果不改写为个人或单条内容成果。
- 精华油和面膜的重建话术继续标注；防晒已有历史话术不误标为重建。以各项目具体来源为准，不做全站一刀切。
- 复盘说明、重建示例和历史原稿可区分，展示分组不冒充当时发布顺序。
- 标题与正文使用具体任务、判断和作品，减少空泛能力口号、重复解释与开发术语。
- 目标岗位、案例顺序和视觉方向可以作为改版提案，未明确的部分不写成 owner 已确认。

## 5. 目录与素材

- 新文件通常使用英文小写与连字符；保留已有路径和原件中文文件名，不为统一命名批量迁移。
- 新增案例素材优先放入对应项目的 `assets/` 分类目录；网页预览图使用 `portfolio-previews/` 或项目内明确的预览目录。
- 原件、网页查阅副本、预览图分别标识。压缩和裁切作用于展示副本，不无声替换原件。
- 文件移动、替换和归档前搜索实际引用，核对历史链接、线稿配对及来源说明；保留必要兼容入口。
- 更新已有素材清单时沿用其字段，并同步路径、大小与校验信息。尚未提供的原件不记录成已入库。
- 图片不拉伸；长图用可读节选或预览与完整查看入口。关键文案不能只依赖一张缩得过小的长图。
- 视频使用可控制的播放器、适当封面与按需加载，不默认自动播放；沿用已处理的录屏副本，保留声音、时间轴及必要遮挡。
- 不用 AI 补造历史作品、原稿或截图中的小字。完整对话、凭据、个人通知和不属于公开作品集的内部材料不提交。

## 6. 实现与页面体验

- 首轮沿用 HTML/CSS/JS 与 GitHub Pages；新增框架、依赖、构建或服务时，说明任务必要性和维护影响，避免无关扩展。
- 优先复用现有布局、组件及颜色／字号变量；新样式围绕组件组织，避免持续新增覆盖文件或到处加入全局规则。
- 新增普通多行代码采用两空格缩进；现有压缩或紧凑代码只调整本次涉及部分，不为排版制造整文件差异。
- 保留 `index.html` 中脚本依赖顺序和样式加载顺序；修改 JS/CSS 后更新对应资源版本参数。
- 动态内容继续经过适当转义。导航使用链接，动作使用按钮，输入和控件有清楚的可访问名称。
- 每个渲染页面有清楚的主标题；正文、辅助文字和图片说明有可读层级。新设计中文正文通常从 16px 起评估，较小文字需要实际检查。
- 手机页面避免意外横向溢出，菜单和长图有清楚的操作入口；关键内容不只靠悬停显示。
- 保持可见键盘焦点、图片替代说明、弹窗关闭与焦点返回；尊重减少动态效果的系统偏好。
- Hash 深链、刷新、返回／前进及旧路由兼容按影响检查；页面标题和分享信息与当前发布方式一致。
- 加载性能根据实际页面测量；资源仓库总大小不能直接当作首屏下载量。

## 7. 按改动范围验证

| 改动 | 必要检查 |
| --- | --- |
| 纯文档／规范 | 文件引用、来源与状态一致性、Git 空白错误；不要求重做页面测试 |
| 文案／数据 | 职责与指标口径、资源路径、受影响页面实际呈现 |
| 图片／视频／PDF | 引用、配对、可读性、播放器／文件入口和展示副本状态 |
| 模板／路由／交互 | 相关 JS 语法、受影响用户路径、控制台、键盘行为与旧入口 |
| CSS／布局 | 受影响页面的桌面和手机视口、文字、长图、控件及横向溢出 |

基础命令：

```bash
git diff --check
node --check portfolio-2026-content.js
node --check portfolio-2026-wireframes.js
node --check portfolio-2026.js
```

后三项用于 JS 改动的语法检查，不代表浏览器运行验证。页面预览方法见 README。

布局改动优先覆盖 375px、768px、1280px 等代表视口；浏览器模拟与真实手机检查分别记录。只执行静态检查时，不宣称已完成页面、手机或性能实测。

验证通过后，仅在新增修改、失败或未解决疑点存在时扩大检查。交付前按协作文档整合最新远端更新，再验证受影响部分。
