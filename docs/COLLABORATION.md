# 日常协作

更新日期：2026-11-02。

共同仓库：https://github.com/yanpingsun/yanping-portfolio-site

本项目只有两位人类协作者：仓库 owner 与另一位协作者，两边都可能使用 agent。owner 没有开发和 Git 使用背景，负责说明需求、提供素材和确认事实；agent 负责整理文件、实现、版本同步与交付。双方都遵守同一份 AGENTS 和本流程，不额外划分复杂角色。当前使用 GitHub。

## 使用 GitHub

1. 检查本地状态、当前分支和相关 PR，保留本地未提交修改；读取最新协作规范。
2. 获取远端最新 main 和相关任务分支，比较并整合更新。新任务以最新 main 为基础建立自己的任务分支；已有任务保留本地工作并整合远端变化。双方不同时写同一个任务分支。
3. 修改本次任务需要的文件。提交前检查差异，确认新增、修改和删除均符合本次意图，再运行对应检查并提交。
4. 推送或交付前再次获取远端更新，整合对方新提交，检查受影响部分，再推送自己的任务分支并创建或更新 PR。推送被拒绝时先查明原因，不用强制推送绕过他人改动。
5. 相同位置的修改逐项比较；普通技术合并由 agent 处理，涉及事实或业务取舍等无法判断的情况再问人。合并会影响正式页面时，先按下方预览与发布约定处理，再按本次明确授权执行。
6. 交付说明改了什么、检查了什么，以及文件是在本地、共享分支、main 还是正式站，不把“已上传”笼统当作全部完成。

“先拉最新，再修改、提交和推送”是一般原则；具体可由 agent 使用 fetch 后整合，或在状态合适时使用 pull，不要求 owner 选择命令。一次提交多个文件本身正常，关键是先核对版本和实际差异，保留对方修改。

有终端时使用正常 Git 流程；只有 GitHub 工具时，通过工具创建分支、写入文件和 PR。写入前读取当前版本，写入后核对结果。当前工作区已验证 Git 读取与 GitHub 连接写入可用，命令行 push 缺少认证时直接使用现有连接，不要求 owner 配置 Git。

若拿到的只是文件夹或压缩包，无法确认其对应的仓库版本，先保留副本，以最新仓库为基础识别并整合本次变化。不能把本地缺少的文件当作删除指令；无法判断哪些才是本次修改时，询问具体内容或文件范围。

## 怎样引导自然语言需求

agent 负责把需求转成合适操作，用简单的话解释必要影响并继续；不要求 owner 学会 Git，也不为普通操作增加审批。明确的新要求按实际授权范围执行，含糊的技术用词不扩大成删除或覆盖授权。

| 用户的说法 | agent 的处理方式 |
| --- | --- |
| “把本地全部上传／重新传一遍” | 先同步远端和检查差异，只提交本次实际变化，保留对方新文件与修改 |
| “以本地为准／覆盖 GitHub” | 先核对两边差异；明确指定替换的文档按范围替换。若会舍弃对方或未保存工作且意图不清，说明具体影响再确认 |
| “冲突你帮我解决” | 自主处理普通合并；若两种事实表述无法判断，只问具体哪一项内容准确，不让用户选择 Git 命令 |
| “资料上传了，网站也好了吧” | 区分资料共享、网页接入与实际发布；按 pipeline 和当前任务范围处理，并如实报告状态 |

可建议使用这样的说法：“先同步 GitHub 最新版本，保留另一位协作者的修改，再提交我这次的更新。完成后告诉我文件共享到哪里、网页是否更新。”这只是表达示例，不是必须填写的模板。

## 简单约定

- owner 用自然语言说清是补充资料、替换内容，还是修改网页；不需要填写技术表格。
- 只归档资料时说明页面尚未接入；代码或资料已保存不等于正式站已更新。
- 日常进度写在各自 PR 中，项目阶段变化才更新 docs/PROJECT.md。
- 素材移动、删除或重命名前检查引用；不将模糊的同步要求当作强制推送、丢弃历史或覆盖他人工作的授权。
- 不增加强制接手回执、空白测试提交或额外审批步骤。

## 预览与正式发布

正式站继续沿用现有 GitHub Pages。HTML 阶段先发布独立预览路径，例如 `/preview/general/`，让用户用实际链接查看桌面与手机效果；用户明确确认对应版本后，再替换正式入口，并保留可恢复的旧版节点。当前已通过[PR #4](https://github.com/yanpingsun/yanping-portfolio-site/pull/4)只新增该路径，提供[通用版HTML r1预览](https://yanpingsun.github.io/yanping-portfolio-site/preview/general/)；根目录正式入口未替换。完整内容、UX和生成工具仍在工作分支及原草稿PR评审。

预览也是公开可访问的网页，但不占用原正式入口。只新增预览所需的页面、样式、脚本和数据，原正式页面及其使用的资源保持原样；已有原素材可只读复用。不要为了查看任务分支而切换正式站的 Pages 发布源，也不要把“分支已推送”当成“预览已部署”。发布到独立预览路径本身仍需正常部署与验证；本轮HTML r1按此方式新增预览；以后仍不在内容或UX阶段提前制作代码原型。

日常保存、推送和文档共享继续自主完成；“继续优化”“同步到 GitHub”等表述不代表用户已确认替换正式页面。确认过的版本按授权发布，不为同一次发布重复询问。
