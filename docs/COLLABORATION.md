# 双方 agent 的协作与 GitHub 使用

版本：1.1 · 更新日期：2026-11-01。

owner 不需要懂开发或 GitHub。owner 用自然语言说明需求、提供素材、确认事实与展示效果；agent 根据本次授权完成技术操作，并用业务语言交付结果。

## 人与 agent 的分工

| 角色 | 默认负责 | 交付方式 |
| --- | --- | --- |
| owner | 需求、作品事实、本人职责和页面反馈 | 自然语言与素材文件 |
| owner agent | 归档素材、整理确认稿、记录口径，按明确请求完成网页小修改 | 独立内容分支与交接 PR |
| 技术协作者及其 agent | 页面结构、发布数据、样式、交互、工程规范和变更整合 | 独立技术分支与验证结果 |

默认分工不限制 owner 提出其他修改。范围重叠时，agent 先看对方相关开放 PR，再拆分任务或接续现有任务，避免同时改同一段发布数据。

全局状态和规范由整合任务维护；日常内容任务在自己的 PR 记录进度，不必每次编辑全局项目文件。

## GitHub 在这里的作用

| 名称 | owner 应理解的结果 | agent 要执行的操作 |
| --- | --- | --- |
| 仓库 | 双方共同取得文件与修改记录的位置 | 确认正确仓库、权限和最新版本 |
| 分支 | 正在修改的独立版本，暂不影响正式版本 | 每项独立任务使用自己的分支 |
| commit | 一次可追溯保存，但可能还只在本地 | 检查并保存本次差异 |
| push | 文件已共享，对方可读该分支 | 推送或通过等价接口提交，再核对远端结果 |
| PR | 一份包含改动、验证与下一步的交接单 | 创建、读取差异并整合任务 |
| main 与网站发布 | 正式仓库版本与网站实际结果 | 分别确认合并状态和发布证据 |

GitHub 不是双方电脑之间的实时同步盘。未推送的文件、当前云端目录和聊天附件不会自动共享；新规则也不会自动约束一个尚未读取它们的 agent。

## 第一次接入

1. 转交 [owner agent 接手说明](OWNER-AGENT-START.md)，由 agent 检查仓库访问、连接身份与工具能力；不索取聊天中的密码或令牌。
2. 检查 `main` 是否已有规范 1.1；尚未合入时，先核实规范分支 `docs/project-standards` 存在，再从该分支读取 `AGENTS.md`、本文件和项目状态。
3. 报告实际读取的分支和提交，不把规范分支、自己的任务分支和正式版本混为一谈。
4. 读取对应案例文稿与素材说明，再处理业务任务。owner 无需选择 Git 技术操作。

规范合入 `main` 后，新任务读取最新 `main` 的规则；不能长期依赖旧规范分支快照。找不到规范分支时明确说明，不能假装规则已经共享或已读。

## 一个需求如何走完

1. 判断是资料归档、事实／文案修正、页面更新、设计建议还是发布请求，只询问无法可靠推定的业务问题。
2. 保留已有工作，获取最新 `main` 并查看相关开放 PR，检查是否有人正在修改同一部分。
3. 从最新基线创建独立任务分支；命名可用 `content/<案例>-<主题>`、`feature/<主题>`、`fix/<主题>` 或 `docs/<主题>`。
4. 只修改本次文件，核对来源、资源引用和受影响页面。
5. 在已授权交付范围内推送任务分支并创建 PR。用户只要求本地准备或建议时遵守该范围，报告尚未共享。
6. 技术 agent 核对内容与实现，整合最新 `main`；合并和发布按当前已经授权的交付范围执行，不因用户是 owner 就推定任何任务都已授权发布。
7. 报告资料是否共享、页面是否接入、正式站是否验证更新，附真实分支／PR 链接。

独立需求通常一个 PR，不额外强制建立 Issue。复杂待讨论需求可用 Issue；无需让 owner 手填 GitHub 表单。

## 资料归档与页面更新

| owner 的要求 | owner agent 的动作 | 交接时说明 |
| --- | --- | --- |
| 先保存资料，不改网页 | 更新案例目录、文稿与必要素材清单 | 已归档；页面未接入 |
| 修正事实／职责／指标 | 记录新的确认内容，同步相关文稿，按请求修改发布内容 | 来源变化、哪些页面已更新、是否仍待接入 |
| 替换网页图片或文案 | 更新对应发布数据、资源和必要缓存版本，检查受影响页面 | 旧新对应、验证、合并及发布状态 |
| 调整全站结构或设计 | 整理目标与素材，交由技术任务实施；已授权部分继续推进 | 当前是建议、样板还是已实现 |

owner agent 优先维护对应案例的文稿、`assets/` 和素材清单；全站 CSS、路由与公共组件由技术 agent 统筹。修改 `PROJECTS` 或 `PROJECT_INTROS` 等共享发布数据时，标明具体案例和字段，不整体替换旧版文件。

归档资料可以合入正式仓库，但不代表页面已展示它们。技术方从已共享的分支／PR 读取新材料，不让 owner 重复上传同一份文件。

## 基本约定

- `origin` 指向 `https://github.com/yanpingsun/yanping-portfolio-site.git`。
- `main` 是正式网站分支；本轮工作在 `work/portfolio-revamp` 进行。
- owner 可以通过自己的 agent 继续提交内容与素材。更新写入 GitHub 后，另一方才可读取。
- 采用分支、普通合并与 PR 整合工作，保留双方提交记录。
- 本地准备阶段结束后再推送工作分支；不把准备工作直接推到 `main`。

本文件负责协作与 Git 操作；来源、内容及实现规范见 [项目规范](STANDARDS.md)，AI 执行入口见 [AGENTS](../AGENTS.md)。以下终端步骤面向具备完整仓库的 agent；只有 GitHub 工具时使用后文等价流程。

## 每次开工

先确认当前目录和本地改动，再获取远端状态：

```bash
git status --short --branch
git fetch origin
git log --oneline HEAD..origin/main
```

如有本地未提交改动，先识别并保留，不能以清理工作区为由丢弃。

开始一个可独立交付的任务时，在项目状态中简记本次范围；短小修复用提交说明记录即可。远端新增的素材、文案或规则先阅读，再判断哪些需要合入当前任务。

## 同步 owner 的更新

在本地改动已经提交、工作区干净的当前工作分支上执行。本轮分支为 `work/portfolio-revamp`，后续使用实际任务分支：

```bash
git merge origin/main
```

- 可以自动合并的改动由 Git 整合。
- 文本冲突逐项比较双方意图，完成后重新验证受影响页面。
- 素材冲突先核对实际文件、清晰度和页面引用。
- 职责、成果数字、定位或展示口径发生冲突时，记录来源并交给项目负责人确认。
- 不通过整文件覆盖、强制推送或破坏性重置解决冲突。

本工作区已采用下面的本地 Git 配置。配置不会随克隆自动传递，新工作区首次建立时执行一次：

```bash
git config --local pull.ff only
git config --local push.default simple
```

`pull.ff=only` 避免普通 `git pull` 隐式产生合并；工作分支整合 `main` 使用上面的显式流程。`push.default=simple` 不替代推送前检查分支和目标。

## 改好后的交付

1. 完成当前范围的修改和必要验证。
2. 提交本地改动，再次执行 `git fetch origin`。
3. 如 `main` 有更新，将其合入工作分支并验证受影响部分。
4. 检查 `git diff --check` 与 `git diff origin/main...HEAD`，确认实际交付范围。
5. 确认当前是预期的命名任务分支，且不是 `main` 或分离 HEAD，再推送当前任务分支并创建 PR：

```bash
git push -u origin HEAD
```

6. 按 [PR 模板](../.github/PULL_REQUEST_TEMPLATE.md) 写明任务、实际文件差异、事实依据、素材关系、页面接入情况、验证与下一步。页面改动只附实际生成的截图或预览，并说明是否为手机模拟。
7. 审核后再合并到 `main`，沿用现有 GitHub Pages 发布流程。没有部署结果时只报告已合并，不宣称发布已验证。

owner 在最后一次同步后仍可能提交更新；PR 合并前需要再确认最新状态。出现差异时继续整合，不能把一次拉取当作长期同步完成。

## 没有终端、只有 GitHub 工具的 agent

- 读取最新 `main`、目标文件及版本，再从已读取的基线创建自己的任务分支。
- 使用工具支持的文件／提交接口写入本次差异。二进制素材使用真实文件上传能力，核实文件字节已保存，不在 Markdown 中粘贴 Base64 代替上传。
- 工具支持预期提交或文件版本检查时使用它；版本不匹配先重读比较，不用旧文件直接重试覆盖。
- 多文件写入使用工具支持的事务或顺序；不并行更新同一个文件或分支头。
- 写入后重新读取 GitHub 中的文件、分支与提交，再创建交接 PR。
- 缺少合并、上传或验证能力时，说明具体还缺哪一步，在 PR 中交给技术方接续，不要求 owner 手写 Git 命令或共享令牌。

只有聊天、没有仓库读写工具时，输出待处理文件与业务说明，明确“未写入 GitHub”。不得伪造分支、提交、PR 链接或“已同步”状态。

## 后续分工建议

owner 主要维护事实与素材；技术协作者主要维护页面与实现。开始修改同一份网页内容数据前，先记录本次范围，减少同时修改同一段文字。

这一分工是减少冲突的协作建议，不阻止 owner 修改任何已有内容。拆分与迁移文件前先检查最新引用，必要时保留旧入口。

回退已经共享的提交时优先使用明确的反向提交，并重新核对后续 owner 更新。暂存、提交或合并前都先查看差异，不能把与当前任务无关的修改一并交付。
